## 架构判断

当前有效主线为：

```text
任务路由
  → 原始材料登记、证据画像、问题分解
  → LLM 生成 ModelIR
  → LLM 审查与修订
  → 确定性编译、注册算子执行
  → 执行 / 证据 / 模型适用性验证
  → Guidance 与交付包

Polish → 共享写作、图表、导出与审计支持
```

这个骨架值得保留。本次拆分改善了实现归属，下一轮收益最大的工作是补齐“材料如何变成数值”和“题意如何变成方程”两处边界。

### 高优先级：已有方程的求解正确性与题意完整性仍有距离

`backend/app/guidance/model_validation/milp.py` 的 `milp_feasibility` 根据编译后的矩阵重算约束违背量。它可以发现已登记约束被违反，却不能单独证明业务必需的方程已经写入矩阵。

上一轮架构实验从 `generic_multiperiod_inventory.json` 删除 `initial_balance` 与 `state_balance`，保留合法问题、证据和需求事实绑定；变体仍通过事实覆盖、语义验证、编译、算子执行和全部 5 项 MILP 适用性检查。本轮没有重跑该临时实验，也没有将其新增为仓库回归测试。

该实验没有调用 LLM Reviewer，也没有覆盖真实生成的完整流水线。因此能确认的是确定性验证的边界，不能据此断言完整流水线一定放行错误模型。数学完整性目前仍较依赖 Reviewer。

### 高优先级：精确核验还不是统一的数据物化

`backend/app/guidance/parameter_evidence.py` 已能精确比对已登记的标量与表切片，但静态数组仍主要由 LLM 提供。

上一轮使用真实 Excel 的实验表明：工作簿已登记不代表证据画像中包含可直接解析的完整数值表。正确数组也可能被静态来源校验拒绝。本轮没有重跑该临时实验。现有 Excel 读取算子及相关测试确实存在，因此问题是静态绑定与运行时读取尚未统一，不能概括为“不支持 Excel”。

### 中优先级：算子描述与执行契约仍不完整

本轮复核 `backend/app/guidance/operators.py`：`OperatorDefinition` 描述输入输出端口、版本、前提条件及校验器，但没有参数结构和输出内部字段结构。`model_generation.py` 仍向生成阶段提供 `available_operator_ids`。这些信息尚不足以共享一份完整的生成、校验与运行契约。

这更适合围绕选定问题类型逐项补齐，而非立即泛化全部算子。
